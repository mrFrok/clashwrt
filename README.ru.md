## Возможности

| | |
|---|---|
| 🧭 **Четыре режима перехвата** | TPROXY работает не на всех ядрах, поэтому для каждого случая есть рабочая замена — и **тест, который говорит, какой режим выбрать**. |
| 🪄 **Мастер настройки** | Вставьте ссылку на подписку или ссылки узлов, выберите DNS и маршрутизацию — получите рабочий `config.yaml` с входами под выбранный режим. |
| 💾 **Влезает в маленькие роутеры** | Ядро на 55 МБ можно хранить **сжатым на флеше** (22 МБ) или **только в RAM**; дашборд тоже. Установщик сам считает, что поместится. |
| 🔐 **Проверка загрузок** | Ядро и обновления ClashWrt должны совпадать с SHA-256, который GitHub указывает для файлов релиза. |
| 🚀 **Обход в ядре** | То, что и так идёт напрямую, минует mihomo прямо в ядре — для такого трафика работают **flow offloading** и **SQM**. |
| 🛡️ **Защита от утечек** | Пока прокси включён, блокируются IPv6, DNS-over-TLS и (по желанию) DNS-over-HTTPS. |
| 🔀 **Разделение TCP/UDP** | UDP через Hysteria2/TUIC, остальное через Reality/VLESS — одной кнопкой, на любом конфиге. |
| 🧯 **Выключатели и watchdog** | Прокси, ядро или всё сразу — одним щелчком; watchdog (по желанию) пускает напрямую — или блокирует — когда VPN падает. |
| 📝 **Редакторы с проверкой** | Конфиг и списки правил проверяются `mihomo -t` до установки, с резервными копиями. |
| 🌐 **Английский и русский** | Весь интерфейс. |

ClashWrt отвечает только за файрвол и маршрутизацию. Ваш `config.yaml`, узлы и правила остаются вашими: мастер пишет конфиг, только если попросить, редакторы проверяют его перед записью, и ничего не переписывается у вас за спиной.

## Требования

- **OpenWrt 22.03 или новее** с файрволом **fw4/nftables**; подходят и `apk` (25.12+), и `opkg` (23.05/24.10). На 21.02 и старше (fw3/iptables) установщик отказывается, а не ставит правила, которые файрвол молча проигнорирует.
- `nftables`, `ip-full`, `kmod-nft-nat`, `kmod-tun`, `curl` — установщик доставит недостающее. `kmod-nft-tproxy` нужен только режимам TPROXY, `socat` — только тесту TPROXY.
- Ядро mihomo, скачивается под ваш процессор: arm64, armv5/6/7, x86_64, i386, mips/mipsel, mips64/mips64el, riscv64.

**Место.** Работающий mihomo сам занимает 60–90 МБ RAM. Где лежит его файл на 55 МБ — решаете вы:

| Ядро хранится | Флеш | Доп. RAM | Нужно |
|---|---|---|---|
| на флеше | ~60 МБ | — | любой объём RAM |
| сжатым на флеше | ~22 МБ | ~55 МБ | от 256 МБ RAM |
| только в RAM | — | ~55 МБ | от 256 МБ RAM и доступ к GitHub при загрузке |

Роутер со 128 МБ RAM *и* маленьким флешем не потянет mihomo вовсе — дайте ему флеш через [extroot](https://openwrt.org/docs/guide-user/additional-software/extroot_configuration) на USB-флешке.

Разрабатывается и проверяется на OpenWrt 25.12, BananaPi BPI-R4 (`mediatek/filogic`). Пакеты и API LuCI для 23.05 и 24.10 сверены на совместимость; если там что-то не так — откройте issue.

## Установка

```sh
wget -qO- https://raw.githubusercontent.com/mrFrok/clashwrt/main/install.sh | sh
```

Установщик показывает объём RAM и свободное место на флеше, а затем спрашивает. **Enter — рекомендуемый ответ**, рассчитанный по этим цифрам:

1. **Версия** — последний релиз (с проверкой SHA-256) или ветка разработки.
2. **Где хранить ядро** — на флеше, сжатым на флеше или только в RAM. Предлагается только то, что помещается.
3. **Дашборд** — metacubexd, zashboard, Yacd-meta или без него, и где его хранить.
4. **dnsmasq-full** — чтобы набор обхода брал домены из вашего конфига.

Перед изменениями показывается сводка и вопрос «Продолжить?». После установки ничего не включается: **трафик не перехватывается, пока вы сами не включите прокси**, поэтому неудачная установка не уронит сеть. Повторный запуск обновляет на месте и сохраняет настройки.

Дальше: **Службы → ClashWrt**, мастер настройки, затем включить прокси на странице «Обзор».

> [!NOTE]
> Вопросы читаются с терминала, даже когда скрипт пришёл через конвейер. Без терминала — например, кнопкой **Обновить** в LuCI — ничего не спрашивается, берутся прежние ответы. Если процессор не распознан, установщик спросит название сборки mihomo (`uname -m` пишет `mips` для обоих порядков байт, поэтому сначала читается `DISTRIB_ARCH` самого OpenWrt).

### Обновление

В «Обзор» → «Обслуживание» есть кнопка для каждой из двух частей, которые обновляются отдельно. Там же видно установленную версию mihomo против последней и версию ClashWrt против последней.

- **Обновить ядро** скачивает сборку mihomo под этот процессор, кладёт её туда, куда указано в «Настройки» → «Хранение», и перезапускает демон, если он работал.
- **Обновить ClashWrt** заново запускает установщик. Он сохраняет `/etc/config/clashwrt`, `config.yaml` и ядро, а также то, было ли ядро включено при загрузке. Работает в фоне с журналом на странице: он заменяет страницы LuCI и перезапускает `rpcd`, так что в конце придётся войти заново.

**Каждая загрузка проверяется.** GitHub хранит SHA-256 для каждого файла релиза. Ядро, чей `.gz` не совпал, не устанавливается (`core_verify '0'` разрешает релизы, для которых GitHub хэша не даёт). Релиз ClashWrt несёт свой архив и установщик, и они тоже должны совпасть. Это ловит загрузку, испорченную, оборванную или подменённую по пути — например, на прокси-узле. От релиза, плохого изначально, это не защищает: ни mihomo, ни ClashWrt релизы не подписывают. Ветке разработки сверяться не с чем, и она об этом пишет.

**Загрузки идут сначала через прокси** и только при неудаче напрямую, так что заблокированный или медленный GitHub обновлению не мешает. В конфиге мастера для этого есть вход `clashwrt-fetch` на `127.0.0.1:7899`: всё, что приходит туда, идёт в группу `Proxy` независимо от правил. Конфиг, написанный вручную, использует свои `mixed-port` или `socks-port`. `fetch_via_proxy '0'` — качать напрямую. Проверки watchdog намеренно идут напрямую: они проверяют VPN снаружи.

```sh
/usr/libexec/clashwrt/updctl.sh core-status          # установлено / последнее, и где лежит
/usr/libexec/clashwrt/updctl.sh core-install         # последний релиз
/usr/libexec/clashwrt/updctl.sh core-install v1.19.30
/usr/libexec/clashwrt/updctl.sh self-status
```

<details>
<summary><b>Запасные ядра</b></summary>

Файл mihomo весит ~55 МБ: Go вкладывает в него всю среду выполнения. Две копии, оставленные вручную «на всякий случай», занимают большую часть обычного оверлея — а оставлять копию естественно, поэтому они копятся.

После успешного обновления ядра запасные удаляются. Критерий узкий: файл в `/usr/bin` с именем `mihomo…`, не живой `/usr/bin/mihomo`, не запущен и на вопрос о версии отвечает, что он Mihomo. Ядро с другим именем — например, `sing-box` — не трогается никогда. Каждое удаление печатается.

```sh
/usr/libexec/clashwrt/updctl.sh cores        # что есть и что работает
/usr/libexec/clashwrt/updctl.sh prune-cores  # удалить запасные сейчас
KEEP_OLD_CORES=1 ... core-install            # обновить, ничего не удаляя
```

</details>

### Удаление

```sh
wget -qO- https://raw.githubusercontent.com/mrFrok/clashwrt/main/uninstall.sh | sh

KEEP_CORE=1 sh uninstall.sh        # оставить mihomo
KEEP_CONFIG=1 sh uninstall.sh      # оставить /etc/mihomo и настройки UCI
ASSUME_YES=1 sh uninstall.sh       # не спрашивать
```

Набор правил снимается *до* удаления скриптов, которые умеют его снимать; созданная зона fw4 удаляется.

## Хранение и память

**«Настройки» → «Хранение и память».** Ядро и дашборд — единственное большое, что ClashWrt кладёт на роутер (около 60 из 65 МБ), поэтому каждое можно хранить тремя способами:

| `core_store` / `ui_store` | На флеше | При загрузке |
|---|---|---|
| `flash` | сам файл / каталог дашборда | ничего не нужно |
| `gz` | `.gz` из релиза (22 МБ) / архив дашборда (2–10 МБ) | распаковка в RAM, без сети |
| `ram` | одна строка с версией | скачивание в RAM |

В режимах RAM `/usr/bin/mihomo` и `/etc/mihomo/ui` становятся символьными ссылками в `/tmp`, поэтому всё, что вызывает `mihomo` по имени, по-прежнему его находит. Переключение сначала копирует, потом удаляет — момента без ядра нет. В RAM ничего не переезжает без явного запаса: у роутера от 256 МБ, свободной RAM остаётся больше max(32 МБ, 15 %), а в `/tmp` — четверть свободного места. Сжатое ядро перед каждой распаковкой сверяется с записанным SHA-256.

> [!WARNING]
> **Только в RAM** — это скачивание при каждой загрузке. Пока GitHub не ответил, ядра нет, и трафик LAN идёт так, как задано в «Когда VPN падает»; скачивание повторяется раз в минуту в фоне, и mihomo запускается, как только ядро появится. **Сжатым на флеше** такого промежутка нет — его установщик и советует, когда флеша мало.

**Память.** ClashWrt где может уменьшает аппетит mihomo:

- **Мягкий предел памяти** для среды Go (`core_mem_limit`): `auto` ставит 48 МБ при RAM меньше 256 МБ и 96 МБ при меньше 512 МБ — сборщик мусора работает чаще, а куча не растёт. За пределом ничего не убивается.
- **Без базы GeoIP.** Частные сети ловятся правилами `IP-CIDR`, а не `GEOIP,private`: иначе mihomo скачивает `geoip.metadb` на 8 МБ — и не проходит проверку конфига, пока GitHub недоступен.
- **Бинарные наборы правил.** Мастер берёт списки geosite/geoip в формате `.mrs` — впятеро меньше YAML и грузятся без разбора.
- **Без поиска процессов** (`find-process-mode: off`): процессы клиентов LAN на роутере не видны.
- **Меньше доменов в dnsmasq.** Имя, родитель которого уже в списке, выбрасывается — dnsmasq и так ловит поддомены (−7 % на Re-filter).
- **Провайдеры в RAM** — только пока RAM позволяет, см. [ниже](#провайдеры-в-ram).

```sh
/usr/libexec/clashwrt/updctl.sh core-store flash|gz|ram
/usr/libexec/clashwrt/uictl.sh store flash|gz|ram
/usr/libexec/clashwrt/updctl.sh core-where           # где ядро, сколько свободно флеша и RAM
```

## Зачем четыре режима

У прозрачного прокси три рабочих механизма, и ни один не работает везде:

| Механизм | TCP | UDP | Заметки |
|---|:-:|:-:|---|
| **TPROXY** | ✅ | ✅ | Правильный. Сохраняет исходный адрес назначения для обоих протоколов без tun. На некоторых ядрах сломан. |
| **NAT redirect** | ✅ | ❌ | Работает всегда, но для датаграмм нет `SO_ORIGINAL_DST`. |
| **TUN** | ✅ | ✅ | Работает везде, но каждый пакет проходит через userspace. |

«Сломанный TPROXY» — не теория. На ядре MediaTek из `mtk-openwrt-feeds` правило nft срабатывает, пакет помечается и уходит в локальную таблицу, счётчик растёт — а сокету `IP_TRANSPARENT` ядро его так и не отдаёт. Conntrack висит в `SYN_SENT [UNREPLIED]`, клиент ждёт. Тот же конфиг на обычном OpenWrt работает. Поэтому режим — это настройка, а не допущение:

| `mode` | TCP | UDP | Когда выбирать |
|---|---|---|---|
| `tproxy` | TPROXY → `tproxy-port` | TPROXY → `tproxy-port` | Ядро поддерживает TPROXY. Быстрее и правильнее всего. |
| `tproxy_tun` | TPROXY → `tproxy-port` | fwmark → tun | TPROXY работает для TCP, но не для UDP. |
| `tun` | fwmark → tun | fwmark → tun | Работает везде. Проще всего. |
| `redirect_tun` | NAT → `redir-port` | fwmark → tun | TPROXY не работает. TCP остаётся на быстром пути в ядре. |

Не гадайте — нажмите **Проверить поддержку TPROXY**:

```
tproxy rule matched : 4 packets
socket received     : 0
client result       : rc=000

FAIL -- the rule matches but the socket never receives the connection.
This kernel cannot be used with TPROXY, no matter how it is configured.
Recommended mode: redirect_tun (or tun)
```

В режимах с tun мастер включает **GSO** для стеков ядра (`system`, `mixed`): mihomo получает целые сегменты по 64 КБ вместо отдельных пакетов — это основная нагрузка на CPU на быстром канале.

## Как пользоваться

| Страница | Для чего |
|---|---|
| **Обзор** | Состояние, текущий узел и задержка, состояние обхода, выключатели, «Обслуживание» (статус, обновления, разделение, дашборд, бэкап) |
| **Мастер настройки** | Собирает `config.yaml` |
| **Конфигурация** | Редактор, резервные копии, файлы правил |

### Обзор и выключатели

«Обзор» обновляется каждые 5 секунд. Под статусом виден узел, который сейчас использует `Proxy` — с проходом через `Auto` до конкретного узла и его последней задержкой, — и состояние набора обхода. **Открыть панель** передаёт панели секрет API, поэтому подключится даже дашборд, который его ещё не видел.

На виду переключатель **Прокси**, остальные — под **Остальные переключатели**:

| Переключатель | Когда выключен |
|---|---|
| Прокси | Убирает правила, которые заворачивают LAN в mihomo. Роутер пересылает напрямую, как будто ClashWrt нет. |
| Ядро | Останавливает mihomo и убирает его из автозагрузки. |
| Всё сразу | Оба, в безопасном порядке: при выключении сначала правила, при включении сначала ядро. |

Выключение ядра при включённом прокси требует подтверждения: LAN заворачивался бы в отсутствующее ядро. Включить прокси при выключенном ядре нельзя.

```sh
/usr/libexec/clashwrt/powerctl.sh status
/usr/libexec/clashwrt/powerctl.sh proxy|core|all on|off
```

### Watchdog

По умолчанию выключен («Настройки» → «Основные»). Демон procd просит mihomo измерить запрос через группу прокси. После `watchdog_fail` неудач подряд (3) он проверяет, что работает сам WAN, и только тогда **пускает трафик мимо** прокси. Если WAN тоже лежит, ничего не меняется — обход бы не помог.

Обход держится не меньше `watchdog_hold` секунд (120) и снимается после `watchdog_ok` удачных проверок подряд (3). Если в течение 10 минут всё повторяется, время удваивается, до `watchdog_hold_max` (900). Первые `watchdog_grace` секунд (90) он только наблюдает, чтобы медленная загрузка не выглядела как авария. Ваш переключатель всегда главнее.

**Когда VPN падает** (`watchdog_action`) задаёт, что делать: `direct` (по умолчанию) пускает трафик мимо прокси; `block` — **kill switch**: трафик LAN куда-либо, кроме самой LAN, запрещается, пока путь не вернётся, а «Обзор» показывает красное **Заблокировано**.

```sh
/usr/libexec/clashwrt/watchdog.sh status|probe|reset
```

<details>
<summary><b>DNS во время обхода</b></summary>

Если dnsmasq роутера пересылает запросы на DNS-порт mihomo, на время обхода эта пересылка убирается (исходный список серверов хранится в `/etc/clashwrt-dns.bak` и потом возвращается), и LAN резолвит через обычный upstream. Если другого upstream у dnsmasq нет, DNS остаётся на mihomo, и «Обзор» об этом предупреждает. Проверке нужен `external-controller` mihomo и группа; оставьте `watchdog_group` пустым, чтобы взять группу из последнего правила `MATCH`.

</details>

### Защита от утечек

Пока прокси включён («Настройки» → «Основные»):

| Параметр | По умолчанию | Что запрещает |
|---|:-:|---|
| `block_ipv6` | вкл | IPv6 из LAN наружу. Перехват только по IPv4, и через IPv6 был бы виден ваш настоящий адрес; устройства переходят на IPv4. |
| `block_dot` | вкл | DNS-over-TLS (порт 853), например «Частный DNS» в Android. |
| `block_doh` | выкл | HTTPS к публичным DoH-серверам ([список dibdot](https://github.com/dibdot/DoH-IP-blocklists), обновляется ежедневно, плюс `doh_extra`). |

Всё отклоняется (reject), а не отбрасывается, поэтому устройства сразу переключаются на запасной вариант. **Несколько сетей LAN:** `lan_device` — это список; добавьте `guest`, `iot` или имя устройства, и каждая сеть будет перехватываться и защищаться.

### Мастер настройки

Собирает `config.yaml` из ссылки на подписку или ссылок узлов (`vless://`, `vmess://`, `trojan://`, `ss://`, `hysteria2://`, `tuic://`). Выберите DNS и маршрутизацию — *всё напрямую, кроме выбранных списков* или *всё через прокси, кроме России* — отметьте наборы правил и примените. Входы всегда соответствуют режиму перехвата.

Встроенные списки: `ru-bundle` и `re:filter` ([legiz-ru](https://github.com/legiz-ru/mihomo-rule-sets)), а также наборы для YouTube, Telegram, Discord, X, Instagram, ChatGPT и Gemini ([meta-rules-dat](https://github.com/MetaCubeX/meta-rules-dat)).

Форма открывается заполненной — прошлыми ответами или тем, что удалось прочитать из установленного `config.yaml`. Ссылки узлов из конфига не восстановить, поэтому мастер предупреждает, прежде чем выбросить встроенные узлы или заменить конфиг, правленный вручную.

**Добавить сайт.** Введите URL, имя хоста или название сервиса (`youtube`, `claude`, `netflix`, …) и нажмите *Добавить*: получатся правила `DOMAIN-SUFFIX` перед списками, в выбранную группу. Известные сервисы раскрываются в свои несколько доменов — огромный geosite ради одного сайта не грузится. **Добавить только в текущий конфиг** вставляет эти правила в конфиг, написанный вручную.

- **DNS.** По умолчанию Quad9 через DoH: в `redir-host` mihomo сам резолвит каждое имя, а по обычному UDP провайдер видел бы — и мог бы подменить — каждый запрос. **Fake-IP** — по желанию: соединения начинаются быстрее, но набор обхода отключается.
- **Стек TUN.** `system` (самый быстрый, по умолчанию), `gvisor` или `mixed` для ядер, где он сбоит, `mips` для медленных MIPS-роутеров.
- **Самый быстрый узел.** Группа `Auto` (`url-test`) следует за самым быстрым узлом с допуском 50 мс; она первая в `Proxy`, которая остаётся группой `select`.

### Разделение TCP/UDP

Hysteria2 и TUIC переносят датаграммы нативно; Reality, VLESS и Trojan туннелируют их поверх TCP. Одна кнопка в «Обслуживании» отправляет UDP в первые, а остальное во вторые — на **любом установленном конфиге**, от мастера или вашем. Файл правится построчно, комментарии сохраняются, результат проверяется до замены.

```yaml
proxy-groups:
  - {name: Proxy,    type: select, use: [sub1], filter: '(?i)(reality|vless|trojan)'}
  - {name: ProxyUDP, type: select, use: [sub1], filter: '(?i)(hysteria|hy2|tuic)'}
rules:
  - AND,((NETWORK,udp),(RULE-SET,ru_bundle)),ProxyUDP
  - RULE-SET,ru_bundle,Proxy
  - MATCH,DIRECT
```

`filter:` — это RE2 из Go, в нём **нет lookahead**: исключения пишите как положительные шаблоны.

### Обход в ядре

Набор адресов, которые минуют mihomo; сверяется в ядре до любой маркировки. Соединение, которого mihomo не касается, остаётся обычным маршрутизируемым, поэтому после первых пакетов его может подхватить **flow offloading**, а **SQM** видит каждое устройство отдельно. Правило `DIRECT` внутри mihomo — не то же самое: такое соединение всё равно заканчивается на роутере и пересылается через userspace.

> [!TIP]
> Трафик, идущий *через* mihomo, ускорить offloading'ом нельзя — его пересылает процессор. Аппаратный offloading (например, PPE у MediaTek) ускоряет только то, что обход пропускает мимо. Переключатель **Flow offloading** на вкладке «Обход» меняет собственный параметр fw4 и показывает, работает ли flowtable программно или аппаратно. SQM с аппаратным offloading'ом не совместим.

Что именно обходит прокси, зависит от поведения mihomo по умолчанию — оно читается из конфига, а не угадывается:

| Последнее правило mihomo | смысл | что минует прокси |
|---|---|---|
| `MATCH,DIRECT` | напрямую, если правило не скажет иначе | всё, кроме списка |
| `MATCH,<группа>` | через прокси, если правило не скажет иначе | сам список |

Если ни конфиг, ни ответы мастера этого не говорят, список отклоняется, а не загружается задом наперёд.

**Ваши правила тоже попадают в набор** (`bypass_set_from_config`, по умолчанию с 1.2.2): `IP-CIDR`, `DOMAIN`, `DOMAIN-SUFFIX` и `RULE-SET` — по направлению. Домены идут через dnsmasq (`nftset=`), которому нужен **dnsmasq-full** — его предлагает и установщик, и вкладка «Обход». Набор сам отключается — тогда всё идёт в mihomo, что стоит только скорости, — если конфиг проксирует то, что набор вместить не может (домены без dnsmasq-full, включённый перехват DNS, `GEOSITE`, `DOMAIN-KEYWORD`…). Блок статуса говорит, что именно.

```sh
/usr/libexec/clashwrt/setctl.sh detect        # направление и откуда оно взято
/usr/libexec/clashwrt/setctl.sh status        # возраст списка, что загружено в ядро
/usr/libexec/clashwrt/setctl.sh from-config   # что добавляет config.yaml и что не смог
/usr/libexec/clashwrt/setctl.sh offload [off|sw|hw]
```

### Провайдеры в RAM

mihomo переписывает провайдеры при каждом обновлении — с Re-filter это десятки МБ в день, а на NAND каждая запись изнашивает память. С `providers_in_ram` (включено по умолчанию) они переезжают в `/tmp` **только пока RAM позволяет** (те же правила, что выше; роутеры меньше 256 МБ не переезжают) и возвращаются на флеш, как только условие перестаёт выполняться. Копия на флеше сохраняется, поэтому после перезагрузки RAM заполняется без скачивания.

### Конфигурация, бэкапы, журналы, дашборд

- **Конфигурация** правит `config.yaml` с проверкой синтаксиса, резервными копиями и восстановлением в один щелчок; «Файлы правил» управляет списками для файловых провайдеров. Ничего не ставится, пока `mihomo -t` не согласится.
- **Резервная копия настроек** («Обслуживание») скачивает один архив с `/etc/config/clashwrt`, `config.yaml` и файлами правил и восстанавливает его — после проверки. Если в копии другой режим хранения, ядро и дашборд переезжают с теми же проверками места.
- **Логи**: журнал самого mihomo из его API (какое правило сработало, какой узел понёс соединение) и системный журнал вокруг.
- **Веб-дашборд**: metacubexd, zashboard, Yacd или любой `.tar.gz` с `index.html`. API слушает все интерфейсы, поэтому каждый конфиг мастера получает случайный `secret:` — введите его в панели.

## Настройки

**Службы → ClashWrt → Настройки** или `/etc/config/clashwrt` — у каждого параметра безопасное значение по умолчанию и пояснение рядом.

```
config clashwrt 'config'
	option enabled '1'            # управляется переключателем «Прокси» на Обзоре
	option mode 'redirect_tun'
	option lan_device 'auto'       # или список: lan, guest, iot …
	option wan_device 'auto'
	option tun_device 'clash-tun'
	option mihomo_dir '/etc/mihomo'
	option self_mark '2'
	option block_ipv6 '1'
	option watchdog '0'
	option core_store 'flash'     # flash | gz | ram
	option ui_store 'flash'
	option core_mem_limit 'auto'  # auto | off | МБ
	option core_verify '1'
```

`auto` спрашивает у netifd, какое устройство стоит за `lan`/`wan`, поэтому переименованные мосты, PPPoE и порты DSA работают как есть. Порты **читаются из `config.yaml`**, так что файрвол не разойдётся с демоном.

Вашему конфигу mihomo нужно, в зависимости от режима:

```yaml
routing-mark: 2          # всем режимам
tproxy-port: 7894        # tproxy, tproxy_tun
redir-port: 7893         # redirect_tun
tun:                     # всем, кроме чистого tproxy
  enable: true
  device: clash-tun
  stack: system
  auto-route: false      # маршрутизацией занимается ClashWrt
  auto-redirect: false
```

`routing-mark` важнее, чем кажется: mihomo помечает им свои сокеты, и цепочка маркировки на этой метке выходит. Без неё соединение mihomo с вашим сервером перехватывается и возвращается в mihomo.

## Как это устроено

ClashWrt создаёт одну таблицу nftables, `inet clashwrt`, с цепочкой маркировки на `prerouting` и (в `redirect_tun`) цепочкой NAT перед цепочкой fw4. Добавляет `ip rule`, таблицы маршрутизации 100 (локальная доставка tproxy) и 151 (маршрут по умолчанию в tun), **зону** fw4 для tun и `route_localnet=1`. При `stop` всё убирается.

<details>
<summary><b>Почему зона, а не правило nft</b></summary>

Пересылаемый трафик в tun и из него судит цепочка `forward` fw4 с `policy drop`. Accept в другой таблице пакет **не** спасает: все базовые цепочки на хуке проходятся по приоритету, и accept одной не мешает следующей отклонить пакет. Симптом сбивает с толку — счётчик вашей цепочки растёт, а `tcpdump -i <tun>` пуст. Зона в UCI переносит решение внутрь fw4, и он сам восстанавливает его при каждой перезагрузке.

</details>

<details>
<summary><b>Ловушка с пропадающим маршрутом</b></summary>

Маршрут в tun (`default dev clash-tun table 151`) привязан к интерфейсу, поэтому ядро удаляет его каждый раз, когда tun пересоздаётся, — при **каждом перезапуске mihomo**. Ошибки нет: помеченные пакеты падают в основную таблицу и уходят мимо прокси, что выглядит в точности как работа. Хук hotplug чинит маршрут в момент появления устройства.

</details>

<details>
<summary><b>Справочник команд</b></summary>

```sh
/etc/init.d/clashwrt start|stop|reload|status
/usr/libexec/clashwrt/fw.sh status|check|detect|selftest
/usr/libexec/clashwrt/setctl.sh detect|status|from-config|offload
/usr/libexec/clashwrt/powerctl.sh status | proxy|core|all on|off
/usr/libexec/clashwrt/watchdog.sh status|probe|reset
/etc/init.d/mihomo start|stop|restart
/usr/libexec/clashwrt/updctl.sh core-status|core-install [версия]|core-store flash|gz|ram|core-where
/usr/libexec/clashwrt/updctl.sh cores|prune-cores|self-status|self-update|log
/usr/libexec/clashwrt/uictl.sh install <имя>|store flash|gz|ram|status
```

Ручная остановка mihomo оставляет правила, и в режимах TPROXY и NAT перехваченный трафик просто перестаёт работать. Пользуйтесь переключателем **Всё сразу** (или `powerctl.sh all off`): он сначала убирает правила.

</details>

## Если что-то не работает

<details>
<summary><b>Всё настроено, но трафик не проксируется</b></summary>

Проверяйте настоящим клиентом за роутером, а не из консоли роутера: цепочка маркировки висит на `prerouting`, а собственные пакеты роутера через него не проходят.

```sh
ip netns add test
ip link add veth-c type veth peer name veth-s
ip link set veth-s master br-lan; ip link set veth-s up
ip link set veth-c netns test
ip netns exec test ip addr add 192.168.1.211/24 dev veth-c
ip netns exec test ip link set veth-c up
ip netns exec test ip route add default via 192.168.1.1
ip netns exec test curl -s -o /dev/null -w '%{http_code}\n' https://1.1.1.1/
```

Потом посмотрите, что mihomo с этим сделал, — на странице «Логи» или `wget -q -O- 'http://127.0.0.1:9090/logs?level=info'`:

```
[TCP] 192.168.1.211:45178 --> 104.21.32.39:443 match RuleSet(refilter_ipsum) using Proxy[XHTTP Reality]
```

> [!IMPORTANT]
> Если `traceroute` показывает настоящие хопы — трафик **идёт мимо** прокси. Действительно проксированный UDP показывает `*`: прокси не порождает ICMP TTL-exceeded.

</details>

<details>
<summary><b>Новый дашборд выглядит как старый</b></summary>

Дашборды ставят service worker, который продолжает отдавать старое приложение. ClashWrt заменяет его на самоудаляющийся, но уже зарегистрированный worker узнаёт об этом только при следующем переходе: обновите вкладку панели один раз.

</details>

<details>
<summary><b>После перезагрузки нет ядра</b></summary>

В режиме **Только в RAM** ядро скачивается при загрузке и в фоне повторяется раз в минуту; попытки видно в `logread | grep clashwrt`. Если GitHub с вашего WAN часто недоступен, переключитесь на **Сжато на флеше**.

</details>

<details>
<summary><b>«Не удалось проверить обновления» / кнопка «Обновить» не срабатывает (1.4.0, 1.4.1)</b></summary>

Две ошибки этих версий, обе исправлены в 1.4.2:

- **Обновление с 1.3.x на 1.4.0 обрывалось в самом начале**, и роутер оставался на 1.3.x: установщик молча завершался на настройке, которой у старых роутеров ещё нет. Нажмите **«Обновить ClashWrt»** ещё раз — теперь встанет 1.4.1 или новее.
- **После 1.4.0/1.4.1 — «не удалось проверить обновления»**, и кнопка обновления отказывается работать: установщик записал адрес архива из релиза вместо адреса тега, и проверка обновлений его не узнаёт. Сама кнопка это не обойдёт, поэтому один раз из консоли — либо переустановите (на все вопросы можно отвечать Enter; на обновление ядра ответьте *no*, если оно не нужно):

  ```sh
  sh -c 'wget -qO- https://raw.githubusercontent.com/mrFrok/clashwrt/main/install.sh | sh'
  ```

  либо только исправьте запись и затем нажмите **«Обновить ClashWrt»**:

  ```sh
  sh -c "sed -i 's#releases/download/\(v[^/]*\)/clashwrt-v[^/]*\.tar\.gz#archive/refs/tags/\1.tar.gz#' /usr/libexec/clashwrt/.install-info"
  ```

Что делало последнее обновление, показывает `/usr/libexec/clashwrt/updctl.sh log`.

</details>

<details>
<summary><b>Пустой системный журнал / кнопка в LuCI ничего не делает</b></summary>

`logread` читает только буфер logd; при rsyslog или syslog-ng журнал лежит в `/var/log/messages` — страница «Логи» это определяет. Если кнопка молчит, повторите то, что делает страница, и поищите отказ ACL:

```sh
ubus call file exec '{"command":"/usr/libexec/clashwrt/fw.sh","params":["status"]}'
logread | grep rpcd
```

</details>

## Переводы

Строки лежат в `luci-app-clashwrt/po/`. Скопируйте `templates/clashwrt.pot` в `<язык>/clashwrt.po`, переведите и соберите `python3 tools/po2lmo.py <po> <lmo>` — это переписанный без зависимостей `po2lmo` из LuCI. Собранные `.lmo` лежат в репозитории, потому что установщик работает на роутерах без Python.
